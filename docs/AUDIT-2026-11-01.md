# Аудит geomask на роутере: баги, риски и варианты лечения

**Дата:** 1 ноября 2026 года, основной снимок роутера — 19:00:52 МСК, уточнения — в течение аудита.  
**Версия:** `1.22.6`, commit `5a373511a25f37798f98ec4650a3fada4809320b`.  
**Режим:** анализ и чтение. **Исправления не вносились.**

> Короткий вывод: система сейчас работает по ряду наблюдаемых путей, но её строгие обещания шире реальной защиты. Самые опасные места — обход общей политики через отдельный restricted-туннель, ложноположительные защитные проверки, ошибки применения/отката конфигов и сломанные переключатели подписок. Результат «проверка зелёная» недостаточен, чтобы считать все маршруты доказанно безопасными.

## 1. Как читать отчёт

- **Подтверждённый текущий факт** — непосредственно прочитан на этом роутере, с указанным снимком.
- **Подтверждённый дефект кода** — конкретная ошибка потока выполнения/формата, иногда воспроизведённая изолированно. Это **не** означает, что авария уже произошла на живой системе.
- **Потенциальный риск** — указан триггер: падение туннеля, сбой API, параллельный запрос, другая сериализация, новая установка. На роутере такой отказ не вызывался.
- **Высокий приоритет** — нарушение обязательного маршрута, потеря управления/восстановления или ложное разрешение опасного действия. Средний — функциональный сбой/недостоверная диагностика. Низкий — ограниченная совместимость/эксплуатация.
- **Область применимости важнее номера:** fresh-install ошибки не объявляются аварией уже настроенного роутера; осознанные решения владельца (например гостевой backup-share) обозначены как принятый компромисс, а не как новая скрытая настройка.
- Все варианты лечения — **предложения для следующего этапа**, не команды на выполнение сейчас.

В подробной части используются стабильные ID: **L** — живое DNS-состояние, **I** — установщик, **R** — маршрутизация/наблюдатели, **P** — панель/RPC. Перекрывающиеся находки сведены ссылками; количество карточек не следует понимать как количество независимых аварий на роутере.

1. Все поставляемые компоненты: установщик и его семь шагов, LuCI-страница и callbacks, 39 RPC-методов, ACL, backend, подписки/слоты, режимы устройств/IPv6/GLOBAL, AI-DNS, синхронизация и демон, guard/hotplug, списки и восстановление, фильтры узлов, YouTube, torrent-admin, VPN-аудит, DNS-аудит, утренняя проверка, обновление/backup/deploy и тесты.

3. Хеши 15 установленных модулей сопоставлены с ассетами сборки с учётом штампа версии, LF и завершающей строки heredoc — **все совпали**. Установщик на роутере совпадает с артефактом `1.22.6`.

### Не выполнялось

- Нет SSH-записи файлов/скриптов на роутер: наблюдение передавалось через stdin Python, результат сохранялся только на ПК.
- Нет установки/переустановки, смены настроек, `PUT/POST/DELETE` к управляющим API, рестартов, firewall reload, запуска mutating watchdog tick/reset/scan.
- Не запускались сетевые проверки через случайно выбранные AI/restricted-полосы; не скачивались подписки и архивы с секретами. Обычный DNS lookup использован только для уточнения формата ответа.
- Не провоцировались падения, гонки, отключение WAN, восстановление backup или новые P2P-сеансы. Нет клиентского packet capture и браузерного E2E каждой кнопки.
- Не проводился аудит исходников сторонних mihomo/hev/MagiTrickle/запрет-менеджера целиком. Проверены границы их использования geomask. Происхождение уже отключённых/включённых вручную групп не устанавливалось.

**Важно:** нельзя честно обещать «найдены вообще все возможные баги» или «после аудита проблем не будет». Это полное покрытие поставляемых функций чтением кода и целевых сценариев, не формальное доказательство всех состояний всей сети.

## 3. Архитектура: как трафик проходит на самом деле

### Трафик приложений

```text
Обычный LAN-клиент
  ├─ fwmark MagiTrickle по домену/назначению → выбранный группой интерфейс
  │    ├─ Mihomo → hev → :7890 → правила mihomo
  │    ├─ AI → hev → :7891 → фиксированная группа AI
  │    ├─ VPN-noP2P → hev → :7892 → фиксированная группа VPN-noP2P
  │    └─ pppoe-wan → прямой выход
  └─ немаркированный трафик → table100 → Mihomo → правила mihomo

Устройство в режиме ai: source-IP → table101 → AI → :7891 → AI
Устройство bypass: source-IP → main → прямой выход
Режим realtz: обычная маршрутизация; реальная timezone — отдельная клиентская задача
```

Ключевое следствие: **правила mihomo не видят всё одинаково**. Попавший в fixed-policy listener трафик не проходит обычную доменную chain. Поэтому исправный `mtrickle_bulk → VPN` не защищает peer, уже отправленный MagiTrickle прямо в `VPN-noP2P`. Исключения устройств расположены выше правил MagiTrickle и тоже меняют итоговый путь.

### DNS

```text
Обычный DNS клиента → перехват MagiTrickle :3553 / основной dnsmasq :53
  ├─ основной default → DoH :5053
  ├─ лишний старый default → :5054 (не слушается)
  ├─ доменные исключения → заданные внешние DNS
  └─ блокирующие/local rules → локальный ответ

DNS AI-устройств (:53) → nft DNAT → 192.168.0.53:5353
  ├─ default → ai-doh :5055 → uid dnsai → mark0x64 → table101 → AI
  └─ скопированные доменные upstreams → запрос самого AI-dnsmasq (не тот uid)
```

DNS сам по себе не обеспечивает нужный exit-IP приложения. Корректность определяется **вместе** DNS, fwmark/source-rule, tunnel/listener, chain и фактически загруженной конфигурацией. Один запрос с роутера через HTTP proxy не является полным тестом пути браузера LAN-клиента.

### Кто хранит состояние

- MagiTrickle владеет своей конфигурацией и назначениями интерфейсов.
- Sync генерирует четыре ruleset и взаимодействует со списками zapret; разные источники могут запустить его одновременно.
- Backend, installer, scanner, torrent/lane изменяют общий конфиг mihomo — общего транзакционного владельца сейчас нет.
- State/cursor/log разных watchdog живут отдельно; успешная запись файла и успешное применение через API часто не разделены в статусе.

## 7. Дополнительная живая DNS-находка

<a id="l01"></a>
<a id="l01"></a>
### L01. Основной DNS содержит мёртвый default-upstream 5054 и такой же backup upstream

**Приоритет: средний сейчас, высокий при отказе/остановке живого DoH. Статус: наличие и отсутствие listener подтверждены; сценарий остановки не запускался.**

- **Факт:** основной dnsmasq имеет default `127.0.0.1#5054` и `127.0.0.1#5053`. Первый порт не слушается; в `doh_backup_server` тоже сохранён старый 5054. Доменные upstreams дополнительно существуют. См. [снимок UCI и listeners](<Y:/openwrt/audit/2026-11-01/router-state.json#L53-L170>), [фактически сгенерированные defaults](<Y:/openwrt/audit/2026-11-01/router-supplement.json#L40-L60>).
- **Почему пока работает:** существует живой 5053 и кэш/доменные маршруты. Наличие второго мёртвого upstream не гарантирует задержку каждого запроса — алгоритм выбора dnsmasq зависит от параметров и состояния.
- **Риск:** после остановки/переинициализации https-dns-proxy восстановление сохранённого backup-list способно вернуть систему к одному неработающему default. Не все имена перестанут отвечать одновременно: кэш и специфические исключения маскируют проблему.
- **Лечение A (наименее инвазивное):** согласовать основную и сохраняемую резервную upstream-конфигурацию, удалить только подтверждённое наследие 5054, не трогая AI-instance и доменные/рекламные исключения. Команда UCI называется **`del_list`**, не `del-list`: прежние неудачи с дефисом не доказывали отсутствие поддержки удаления списков в сборке.
- **Лечение B (больше устойчивости):** несколько проверяемых DoH-upstream с независимым bootstrap и единым владельцем их lifecycle; резерв не должен нарушать условие AI-only.
- **Лечение C (не выбирать без согласования):** plaintext DNS fallback повышает доступность, но меняет конфиденциальность/географию DNS. Это не безопасный универсальный ответ.
- **Контроль после лечения:** свежие cache-miss запросы обычных и AI-клиентов, корректность adblock, controlled stop/start DoH **на стенде**, отсутствие DNS/main fallthrough у обязательных AI-путей.

### Уточнение прежних объяснений DNS

Два `force_dns=1`, `force_ip_family=auto` или правило `redirect to :53` сами по себе **не доказывают DNS-петлю**. Последнее — обычный способ принудить клиента использовать локальный DNS. Петля доказывается конкретным циклом зависимостей upstream/bootstrap/interception. `auto` может быть нормальной настройкой; фиксация IPv4 — выбор совместимости, не универсальная антипетлевая защита. Отсутствие секции `dns:` у mihomo также не доказывает ни отсутствие утечки, ни наличие проблемы. Проверять нужно фактический граф и отказы. Нынешняя диагностика слишком часто заменяет этот анализ эвристикой — см. R28/R29.

## I — Установщик, системная интеграция и достоверность проверок

<a id="i01"></a>
### I01. Новый конфиг ссылается на группу VPN, которую сам не создаёт
**Приоритет: высокий. Статус: подтверждённый дефект шаблона; текущий настроенный роутер имеет эту группу и этим конкретным дефектом не затронут.**

- **Где:** [генерация групп](<Y:/openwrt/geomask/geomask.sh.in#L449-L469>), [правило torrentdirect](<Y:/openwrt/geomask/geomask.sh.in#L514-L525>), [инициализация rulesets](<Y:/openwrt/geomask/geomask.sh.in#L540-L551>).
- **Что происходит:** свежий шаблон создаёт только `VPN-noP2P` и `AI`, но направляет `RULE-SET,torrentdirect,VPN`. До проверки создаются только `mtrickle/ai/ytdirect/ytvpn`; файлы `torrentdirect` и `torrentsites` на чистом роутере ещё отсутствуют. Проверка step7 также безусловно требует группу `VPN`.
- **Последствие:** установка с нуля не является проверенной рабочей конфигурацией; на готовом роутере ошибка скрыта исторически созданными группами и файлами. При восстановлении после потери конфига возможен отказ запуска.
- **Лечение A (предпочтительно):** явные профили «две подписки» и «три подписки» с согласованными группами, файлами и защитной политикой. В двухподписочном профиле P2P — только разрешённый маршрут либо REJECT.
- **Лечение B:** требовать назначения третьей подписки до включения P2P и не генерировать ссылки на несуществующие политики.
- **Проверить после лечения:** установка в пустой root с настоящим парсером mihomo, без старых rulesets и без сетевого скачивания секретных подписок.

### I02. В нескольких местах проверяется старый конфиг вместо кандидата

### I03. Обещанный безопасный restart не гарантирует возврат к предыдущему рабочему состоянию

### I06. Общая гарантия «полный backup до любого изменения» не соблюдается самим установщиком
**Приоритет: высокий. Статус: подтверждён порядком вызовов.**

- **Где:** [начало reinstall](<Y:/openwrt/geomask/geomask.sh.in#L1615-L1644>), [backup лишь в step4](<Y:/openwrt/geomask/geomask.sh.in#L858-L861>), [обход через --step](<Y:/openwrt/geomask/geomask.sh.in#L1698-L1706>).
- **Механизм:** reinstall сначала удаляет части системы, записывает панель и меняет mihomo, и лишь затем step4 вызывает `ensure_backup()`. Отдельные шаги geo/sync также пишут файлы без обязательного полного preflight-backup. Файловые `.bak` не заменяют полный бэкап.
- **Последствие:** автоматически полученная копия может отражать уже частично изменённую систему. Откат к состоянию до операции не гарантирован.

- **Лечение B:** явный externally-verified backup token для обслуживающего скрипта, с доказуемым сроком действия и архивом на ПК.

### I07. Backup может стать неполным и последняя копия удаляется до успешного создания следующей
**Приоритет: высокий для восстановления. Статус: подтверждён реализацией.**

- **Где:** [ensure_backup](<Y:/openwrt/geomask/geomask.sh.in#L573-L599>).
- **Механизм:** предыдущий архив удаляется заранее. При отказе `sysupgrade` включается `tar ... etc`, но результат получает такое же имя и преподносится как полный LuCI-restorable backup. Он не включает `/root`, где находятся важные компоненты/состояние, и не имеет манифеста полноты.
- **Последствие:** успешный код возврата не означает обещанное полноценное восстановление. Неудачный перенос или нехватка места могут оставить без последней on-router копии.
- **Лечение:** собирать архив без включения старых архивов (явное исключение каталога), проверить список/целостность/обязательные файлы, только после успеха атомарно менять актуальную копию. Не выдавать minimal-tar за полный backup: отдельный тип, предупреждение, запрет рискованных операций.

**Приоритет: высокий по безопасности. Статус: подтверждённая конфигурация; это ранее принятый владельцем компромисс, не скрытая новая уязвимость.**

### I11. AI-DNS не полностью изолирован: доменные исключения уходят мимо маркированного DoH
**Приоритет: средний/высокий в зависимости от требования к DNS-геолокации. Статус: подтверждён путь обхода; внешний перехват пакетов не выполнялся.**

- **Лечение:** актуальная карта владельцев файлов/таблиц/служб, manifest версий и зависимостей, явные режимы install/upgrade/repair; учёт legacy-компонентов; ротация локальных файловых `.bak` отдельно от истории на ПК. Не удалять legacy автоматически без разбора его роли.

<a id="i16"></a>
### I16. Миграция ytwatch-конфига работает с разными путями в тестовом префиксе
**Приоритет: низкий для живого роутера, средний для достоверности тестов. Статус: подтверждён кодом.**

- **Где:** [добавление отсутствующих ключей](<Y:/openwrt/geomask/geomask.sh.in#L1183-L1203>).
- **Механизм:** `save_stream /tmp/...` уважает `GM_PREFIX`, но Python читает жёстко `/tmp/geomask-ytwatch.conf.new`. В песочнице это разные файлы; исключение превращается в `_added=0`, то есть «сохранили имеющееся». На реальном роутере без префикса пути совпадают.
- **Последствие:** тесты не подтверждают корректность миграции, хотя строковые проверки PASS. Параллельные обновления используют одно и то же временное имя.
- **Лечение:** один явно передаваемый путь кандидата, уникальное временное имя, lock и атомарная запись; не превращать ошибку чтения в «новых опций нет». Тестировать сохранение старых значений и добавление недостающих на реальных fixtures.

<a id="i17"></a>
### I17. В свежем шаблоне controller слушает всю сеть без секрета
**Приоритет: высокий для свежей установки. Статус: подтверждена генерация; текущий роутер защищён Bearer, не заявляется как открытый сейчас.**

- **Где:** [параметры свежего конфига](<Y:/openwrt/geomask/geomask.sh.in#L397-L410>), [результат извлечения шаблона](<Y:/openwrt/audit/2026-11-01/installer-evidence.json>).
- **Механизм:** генератор выводит `external-controller: 0.0.0.0:9090`, но не создаёт `secret`. После устранения прочих fresh-install ошибок такой профиль допускает управление из доступной сети без авторизации. Имеющийся секрет старого файла при полном пересоздании также не переносится.
- **Последствие:** клиент, которому доступен controller, способен менять режим/выбор маршрута; это обход доверия к панели и её ACL. Доступность с WAN не проверялась и не подразумевается.
- **Текущий факт:** без Bearer API `/version` и `/proxies` отвечает **401**, ключ присутствует; конкретно живой controller не объявляется незащищённым.
- **Лечение A:** controller только loopback, админский доступ через LuCI/SSH-forward.
- **Лечение B:** непредсказуемый secret и firewall allowlist доверенного управления, сохранение секрета при миграции. Не открывать controller всем LAN-клиентам только потому, что сеть домашняя.

## Высокая важность: маршруты и гарантии

<a id="r01"></a>
### R01. Прямая VPN-noP2P-lane обходит всю защиту torrent/IP внутри Mihomo

**Высокая, подтверждено; срабатывание зависит от назначения групп на netdev.** [lane:9–17](<Y:/openwrt/geomask/assets/geomask-lane.sh#L9-L17>) создает отдельный tunnel→listener→`proxy: VPN-noP2P`; [listener:94–95](<Y:/openwrt/geomask/assets/geomask-lane.sh#L94-L95>) фиксирует группу. MagiTrickle направляет fwmark-трафик непосредственно в этот netdev. [sync:159–170](<Y:/openwrt/geomask/assets/sync_mtrickle_mihomo.sh#L159-L170>) лишь печатает WARN о диапазонах; [sync:241–248](<Y:/openwrt/geomask/assets/sync_mtrickle_mihomo.sh#L241-L248>) переносит IP в tolerant-файл, но этот перенос действует только для входа в обычную rule-chain.

**Триггер/путь/последствие:** subnet в активной MagiTrickle-группе с интерфейсом VPN-noP2P → любой peer в диапазоне → restricted listener, не читая `ai`/`torrentdirect`/`mtrickle_bulk`. Предупреждение проверяет только IPv4-форму текста, не `subnet6`, и не запрещает такую конфигурацию. Domain-only тоже не является доказательством «не P2P»: домен может обслуживать tracker/WebTorrent; sniffing не классифицирует разрешенность приложения.

**Варианты лечения:** A) запретить IP/subnet6 и peer-capable группам restricted netdev, валидировать перед сохранением; B) убрать fixed-policy lane, направлять ее в единую chain с fail-closed политикой; C) разрешать restricted только по положительному списку сервисов/типов трафика, все неизвестное — tolerant/REJECT. Одного предупреждения или лог-аудита недостаточно.

### R06. Неудачный reload sync оставляет старую активную политику навсегда, до другого изменения

<a id="r28"></a>
### R28. DNS pin-check посылает диагностику не в тот lane и вообще не проверяет pinned IP

**Высокая, подтверждено и частично воспроизведено офлайн.** [dnscheck:110–117](<Y:/openwrt/geomask/assets/geomask-dnscheck.sh#L109-L117>) считает tunneled любой DOMAIN-SUFFIX во **всех** yaml, включая DIRECT ytdirect/torrentsites и неиспользуемые stale файлы; не учитывает exact DOMAIN/IP/CIDR/order/listener policy. [via_chain:122–128](<Y:/openwrt/geomask/assets/geomask-dnscheck.sh#L118-L131>) пробует AI7891, restricted7892 и torrent7894 без проверки разрешенности направления. AI может быть признан healthy через restricted, non-AI может уйти в AI; DIRECT tracker, ошибочно помеченный tunneled, при неуспехе первого пути может диагностически попасть в запрещенную подписку.

Проверяется `https://hostname/`, **не IP из hosts**; HTTP CONNECT передает hostname proxy, который разрешает его сам. Никакого `--resolve`/CONNECT_TO/pinned-destination нет. Любой HTTP502, попавший в `%{http_code}`, считается reachable, потому что принимается любой digit code!=000; происхождение/содержимое ответа не проверяются. Воспроизведено: mocked502 на AI7891 дает aliveTrue. Это проверка условия функции, а не утверждение, что конкретная ошибка HTTP CONNECT обязательно отображается curl именно как502 (она может дать000). Дедуп поIP ([140–145](<Y:/openwrt/geomask/assets/geomask-dnscheck.sh#L134-L147>)) проверяет только первый alias и может скрыть отдельный нерабочий сервис.

**Варианты:** A) pin-check строго по ожидаемому effective lane, без fallback между подписками; B) сохранять TLS SNI/Host, но фиксировать **тот самый** pinned destination на proxy dial (проверенный SOCKS/CONNECT контракт); C) отличать proxy error от origin response и оценивать ожидаемый origin fingerprint/status; D) неизвестный lane не пробовать автоматически. Read-only по файлам не означает безвредность сетевого трафика.

### R29. DNS audit способен вывести healthy при неработающем DNS/мертвых pins

**Средняя/высокая как gate. Жесткий LAN192.168.0.1, только первая DoH-instance и AF_INET для bootstrap не отражают прочие конфиги.

**Варианты:** A) валидный DNS client с разбором answer/rcode и exit status; B) Python возвращает structured counters/rc, shell объединяет; C) корректный UDP query/response validation или штатный resolver tool; D) честно разделить no-network/config-only и active probes.

## Общие эксплуатационные ограничения, не потерянные при разборе функций

- Controller secret parsing надежен только у sync. Torrent/yt/vpn/node/morning/lane используют разные regex, не поддерживающие все quoted YAML values. Поэтому валидная смена секрета на строку с пробелом/экранированием может одновременно сломать reload, status и safety checks. Лечение: единый контракт parser/helper без передачи секрета в argv; HTTP failures сохранять как ошибки, а не пустые данные. Основания: [torrent:50–65](<Y:/openwrt/geomask/assets/geomask-torrent.sh#L50-L65>), [node:329–338](<Y:/openwrt/geomask/assets/geomask-node-scan.sh#L329-L338>), [yt:132–139](<Y:/openwrt/geomask/assets/geomask-ytwatch.sh#L132-L139>), [morning:16–17](<Y:/openwrt/geomask/assets/geomask-morning-check.sh#L14-L17>), [lane:110–113](<Y:/openwrt/geomask/assets/geomask-lane.sh#L107-L114>).
- Shared fixed temporary files и отсутствие locks относятся также к state/cursor и crontab read-modify-write. Нельзя считать `os.replace` защитой всей транзакции: оно атомарно только для одного rename.
- Числовые конфиги node/yt/vpn и lane env не имеют общего strict schema/range validation. Неизвестные CLI arguments часто игнорируются; ошибка конфигурации должна быть явной, особенно в --status и safety gate.
- Hardcoded LAN IP и имена интерфейсов допустимы только как документированный проверяемый профиль конкретного устройства, не как молчаливый переносимый default. Отсутствие TUN/API/file — unknown/failure, а не доказательство безопасного DIRECT.
- В существующих тестах есть текстовые asserts на проблемное quoted default ([tests:799](<Y:/openwrt/geomask/tests/run_tests.sh#L799>)) и на имена маркеров. Это не функциональное доказательство. [Python ytwatch tests](<Y:/openwrt/geomask/tests/test_ytwatch_stall.py>) покрывают classifier, но не mode state machine, API failure, reload retry или real routing. Требуются contract/state-machine tests с этими сценариями.

### P03. Переключатель AI возвращает два JSON и перекрывает ошибку успехом

**Высокий; подтверждено.**

- Источники: [первый ответ:669–671](<Y:/openwrt/geomask/assets/geo-backend.sh#L669-L671>), [ai_sub_use:765–770](<Y:/openwrt/geomask/assets/geo-backend.sh#L765-L770>), [вывод rpcd:104–113](<Y:/openwrt/geomask/assets/geo-sync#L104-L113>), [кнопка AI:339](<Y:/openwrt/geomask/assets/geo-sync-page.js#L339>).

### P04. При смене подписки тестируется старый конфиг, а кандидат устанавливается непроверенным

**Высокий; подтверждена ошибочная последовательность, повреждение потенциально при конкретном URL/header.**

- Источники: [построение кандидата:620–644](<Y:/openwrt/geomask/assets/geo-backend.sh#L620-L644>), [test/mv/reload:645–667](<Y:/openwrt/geomask/assets/geo-backend.sh#L645-L667>).

### P05. Смена подписки дублирует header и переносит HWID из другого провайдера

**Средний; подтверждено по алгоритму, реакция конкретного YAML-парсера потенциальна.**

- Источник: [HWID-патч:622–643](<Y:/openwrt/geomask/assets/geo-backend.sh#L622-L643>).

### P06. Реестр подписок не защищён от собственных разделителей и гонок

**Средний; подтверждено локальной проверкой преобразований; race потенциальна.**

- Источники: [парсер/lookup:679–700](<Y:/openwrt/geomask/assets/geo-backend.sh#L679-L700>), [add/del:731–755](<Y:/openwrt/geomask/assets/geo-backend.sh#L731-L755>), [форма:353–368](<Y:/openwrt/geomask/assets/geo-sync-page.js#L353-L368>).
- URL `https://audit.invalid/a|b` разрешён, `_subs_json` сохранит остаток строки, но `_find_sub_url` использует `$3` и вернёт `https://audit.invalid/a`. Имя удаляет только `|`, не LF/CR; direct RPC с `name="one\ntwo"` создаёт дополнительную строку реестра. Идентификатор выбирается read-then-append без lock; два запроса в одну секунду могут получить один ID. Add/del пользуются общим `.tmp`, удаления и добавления могут потерять друг друга.

- Лечение: JSON/другой структурный формат, запрет CR/LF и разделителя при сохранении старого формата, криптографически/монотонно уникальные IDs, flock/lockdir + атомарное сохранение.

### P07. Нулевой счётчик превращает status в невалидный JSON

### P13. Валидация nodes_set расходится с форматом и позволяет внедрить дополнительные строки conf

### P16. Последний рабочий backup удаляется до создания и проверки нового

**Высокий; подтверждённый алгоритм, потеря восстановления потенциальна при сбое.**

- Источники: [ensure_backup:577–596](<Y:/openwrt/geomask/geomask.sh.in#L577-L596>), [self-update:1066–1081](<Y:/openwrt/geomask/assets/geo-backend.sh#L1066-L1081>), [скачивание/удаление на ПК:29–35](<Y:/openwrt/geomask/fetch_backup.ps1#L29-L35>).

### P25. UI и backend маскируют отказы ACL, failed reload и ok:false как успех

**Средний; подтверждено изолированным вызовом настоящего act().**

- Источники: [декларации без reject:6–45](<Y:/openwrt/geomask/assets/geo-sync-page.js#L6-L45>), [act:1123–1131](<Y:/openwrt/geomask/assets/geo-sync-page.js#L1123-L1131>), [syncd callers:854–862](<Y:/openwrt/geomask/assets/geo-sync-page.js#L854-L862>), [global без -f/rc:267–275](<Y:/openwrt/geomask/assets/geo-backend.sh#L267-L275>), [_mihomo_reload:759–762](<Y:/openwrt/geomask/assets/geo-backend.sh#L759-L762>), [rpc wrapper:104–114](<Y:/openwrt/geomask/assets/geo-sync#L104-L114>).
- Без `reject:true` LuCI разрешает Promise числом ubus error (например 6 Access denied). `act()` проверяет только `res.error`, поэтому настоящий тест `act(()=>Promise.resolve(6),...,"success")` создал info-success и вызвал reload. Необъектный ответ не отклоняется; `expect:{}` не проверяет форму. Некоторые отдельные handlers также игнорируют `ok:false`/warn.
- Backend global не использует `-f`, не проверяет transport/HTTP; `_mihomo_reload` заканчивается успешным `sleep 2`, тем самым теряет код failed curl. Wrapper скрывает stderr и не переносит return code backend как явный JSON error. Страница не скрывает mutation-controls у read-only роли; сервер ACL защищает запись, но UI способен сообщить ложный успех после Access denied.
- Эффект: оператор уверен в переключении, которого не было; журнал/внешний вид не объясняют причину. Восстановить гарантию безопасности по зелёной плашке нельзя.
- Лечение: строго типизированный единый ответ `{ok,error,warn,...}`, reject ubus failures, проверка каждого HTTP/exit code, отображение read-only режима и disabled controls. Reload success и active state проверять отдельно от записи файла.

## Security/auth/input validation: что проверено и чего не утверждаем

- LuCI menu зависит от ACL; все 39 backend методов зарегистрированы RPC и выданы соответствующему read/write набору. Не найдено конкретного отсутствующего ACL-метода. Внешняя защита login/session/CSRF не заменялась догадками: browser/ubus endpoint E2E не выполнялся.
- Read API не полностью read-only: [status вызывает _migrate](<Y:/openwrt/geomask/assets/geo-backend.sh#L146-L147>), [subs_list при пустом реестре вызывает seed/add](<Y:/openwrt/geomask/assets/geo-backend.sh#L703-L707>), upd_check пишет cache и запускает внешние HTTP-запросы. Read-only роль таким образом может инициировать запись `/etc/geomask-subs.list` и журналов. Лечение: чистые getters, явная migration/seed write-operation. Это ограниченное нарушение модели прав, не произвольная запись файлов.
- RPC wrapper извлекает jshn-параметры и передаёт shell args в кавычках; из чтения URL/name само по себе не следует shell command injection. Настройки nodes читаются как данные Python, не source shell. Без конкретного source-to-sink такого finding не заявлено.
- URL scheme и ряд enum/MAC/IP-form validations есть; проблемы их полноты указаны P04/P06/P09/P13. URL может быть HTTP/private/localhost, однако это административная функция root-панели; SSRF не вынесен как самостоятельная высокая уязвимость без доказанного отдельного низкопривилегированного пути.
- Основной controller helper не передаёт token в curl argv, корректно разбирает несколько YAML-форм; это положительный факт. Уязвимость отсутствующего auth на текущем контроллере не заявляется: parent runtime отметил 401 без токена.
- Публичные UI external links формируются из LANIP/фиксированных ports, а не произвольного URL подписки; прямого доказанного XSS по ним не найдено. Экранирование JSON не заменяет структуру, но generic XSS/command injection предупреждения не добавлены.

2. Штатная конфигурация сканера P11 и сохранение параметров P12/P13; убедиться, что «skipped by design» не скрывает нулевое пересечение групп.
3. Сохранность/конфиденциальность backup P15/P16, lock/transaction P17, fail-closed update manifest P18.
4. Атомарная доставка stamped release и контроль native exit codes P19, semantic validation/rollback списков P20/P21, listener policy P22.
5. Единая auth/error schema, read-only ACL getters, truthful UI/state timestamps, portability без скрытого системного патча P01/P14/P24–P26.

Непроверенный остаточный риск: успешное поведение на конкретном live-роутере и фактический сетевой эффект требуют отдельного согласованного стендового/E2E прогона; этот read-only отчёт не является разрешением применять предлагаемые изменения к роутеру.
