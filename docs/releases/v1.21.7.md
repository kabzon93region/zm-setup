v1.21.7 - the restored subscription: three fixes found by actually checking

The provider restored the blocked subscription, so for the first time the restricted
lane carries real traffic. Checking it end to end exposed three defects.

1. The nightly scan could not read the restored subscription. The panel answers a
   1.4 KB stub ("Приложение не поддерживается", and a 0.0.0.0:1 decoy node to other
   clients) unless the request carries the provider's own x-hwid header; with it the
   same URL returns 15961 bytes and 42 servers. The scan tried to lift that header with
   one fragile regex and silently sent nothing, so it kept seeing a stub and refusing to
   update the name filter - on a working account, forever. Provider blocks are now parsed
   properly and every header entry is sent in both shapes the config uses.

2. The audit's one number to watch was crying wolf. "bare IPs (P2P-shaped): 20" turned
   out to be 224.0.0.251:5353 - mDNS/Chromecast multicast, which arrives on its own and
   is nothing like a peer. Multicast, broadcast and link-local traffic is now counted
   separately and excluded from the peer-shaped signal, because that signal is the thing
   the owner is told to act on.

3. --check produced a false warning about the tracker ruleset. It still demanded
   "RULE-SET,torrentdirect,DIRECT" after the owner deliberately moved torrent domains to
   the P2P-tolerant VPN lane, and the installer template still generated the retired
   target. Either lane is accepted now and the template matches the live setup.

Also in this release: the AI ruleset follows the interface (v1.21.6) - moving the
Google+AI list onto the AI tunnel had made the sync stop seeing the group entirely and
ai.yaml collapsed from 170 rules to 3, sending Google and AI hosts to DIRECT through the
rule chain. Verified fixed: 219 rules, every tested Google/AI host lands on AI.
